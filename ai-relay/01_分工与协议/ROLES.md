# AI 流水线 · 分工与协议（唯一事实来源）

> 这份文件是**宪法**。Codex、WorkBuddy 与 TRAE 都按这里约定的职责边界协作。
> 修改它 = 修改 Agent 的协作协议。

---

## 一、先回答一个问题：为什么需要多个 Agent？

单个 AI 做完整件事，会遇到一个无解的矛盾：**它既是运动员，又是裁判**。
自己写的 prompt、自己执行、自己验收 —— 验收必然通过，因为它知道自己的意图。

拆成两个角色后，就有了**信息隔离**：

| 角色 | 它知道的 | 它不知道的 |
|---|---|---|
| Codex（出题+阅卷） | 原始需求、验收标准、最终产出 | 执行过程的中间纠结 |
| WorkBuddy（答题） | 优化后的 prompt、验收反馈 | 原始需求者的隐含期待 |
| TRAE（可选执行者） | 阶段指令、项目工作区、验收反馈 | 未分配给它的后续阶段 |

这种隔离让验收变得有意义。**多 Agent 流水线的价值，不只是更快，而是分工和独立验收。**

## 二、职责分工表

| 职责 | Codex | WorkBuddy | TRAE | 说明 |
|---|:---:|:---:|:---:|---|
| 把口语需求改写为结构化 prompt | ✅ 主责 | 可选 | 可选 | 文本型 Agent |
| 定义可量化的验收标准 | ✅ 主责 | 可选 | 可选 | 与 prompt 同批产出 |
| 读取 prompt 并实际完成任务 | 备选 | ✅ | ✅ | 文件夹三的生产者 |
| 操作项目文件 / 调用 IDE 工具 | ✅ | ✅ | ✅ 主责 | 取决于 Agent 环境 |
| 对照验收标准打分 | ✅ 主责 | 可选 | 可选 | 不允许参与自己执行过的任务 |
| 验收失败时写出返工意见 | ✅ 主责 | 可选 | 可选 | 触发有预算的提示词优化循环 |
| 驱动流水线推进 | ✅ 可由脚本调起 | ⚠️ 文件接力 | ⚠️ IDE 文件接力 | 见第四节 |

**一条铁律：验收者不得是执行者。**
若某轮由 Codex 代执行，则该轮验收必须改由其他 Agent 完成，或标记为「自检，可信度降级」。

## 三、为什么这样分？—— 能力边界决定分工

| 能力 | Codex | WorkBuddy | TRAE |
|---|:---:|:---:|:---:|
| 命令行 / API 直接调起 | ✅ CLI | ❌ | ❌ |
| 本地文件协作 | ✅ | ✅ | ✅ |
| IDE 工作区与项目工具 | ⚠️ | ⚠️ | ✅ |
| 可被外部脚本直接编排 | ✅ | ❌ | ❌ |

**结论**：Codex 可通过 CLI 自动调用；WorkBuddy 与 TRAE 使用本地文件接力，需由宿主 Agent/用户完成操作。

## 四、自动化的真实边界（务必读完）

先破除一个错觉：**文件夹不会主动做任何事。**
新建一个文件不会触发任何 AI —— 必须有东西去"看"它。

因此三个角色的触发方式完全不同：

| 环节 | 触发方式 | 自动化程度 |
|---|---|---|
| Codex 优化 prompt | 脚本直接 `codex exec` | 🟢 全自动 |
| 执行任务 | 取决于执行者 | 🟡 见下 |
| Codex 验收 | 脚本直接 `codex exec` | 🟢 全自动 |

**执行环节的两条路：**

- **路线 A（全自动，推荐起步）**：执行者也用 Codex。
  流水线 100% 自动，代价是失去跨模型交叉验证，验收需标记为「自检」。
- **路线 B（半自动，价值最高）**：执行者用 WorkBuddy。
  建立一条定时任务，让 WorkBuddy 每隔一段时间去 `02_prompts/` 取待办、干活、写回 `03_output/`。
  代价是存在分钟级延迟，无法秒级响应。
- **路线 C（IDE 接力）**：执行者用 TRAE。
  看板生成 `_PENDING_FOR_TRAE.md` 与任务专属指令，可打开 TRAE 工作区；你在 IDE 中确认执行并写入交付文件。程序不会假装控制 TRAE 私有 API。

> 你的原方案隐含假设了「文件夹会自己动」。
> 改造后：**文件夹只是消息总线，`orchestrator.py` 才是发动机。**

## 五、目录契约

| 目录 | 谁写入 | 谁读取 | 内容 |
|---|---|---|---|
| `00_inbox/` | 你 | 编排器 | 原始需求（口语即可） |
| `01_分工与协议/` | 你 | 所有 Agent | 本文件，宪法 |
| `02_prompts/` | 文本型 Agent / 编排器 | WorkBuddy / TRAE | 优化后的 prompt、验收标准与接力指令 |
| `03_output/` | 执行 Agent | 验收 Agent | 任务产出 |
| `04_review/` | Codex | 编排器 / 你 | 验收报告 + 返工意见 |
| `_state/` | 编排器 | 编排器 | 状态机、锁、索引 |
| `_logs/` | 编排器 | 你 | 每次调用的完整日志 |

**命名契约**：一切以任务 ID 为锚点，如 `T-20261018-001`。
`02_prompts/T-xxx.md`、`03_output/T-xxx/`、`04_review/T-xxx.md` —— 同名即同任务。

**`RESULT.md` 的优先级（重要）**：
它是流水线的**交付信号**，编排器靠它判断执行是否完成，属于**基础设施**而非任务产出。
因此当 prompt 写有「不要创建其他文件」时，`RESULT.md` **不受该约束限制**，必须照写。
（实测出现过：prompt 禁止额外文件 → 执行者不敢写 RESULT.md → 任务永久卡住。）
编排器已同时放宽为「RESULT.md 存在 **或** 产出目录非空」即可判定交付。

## 六、状态机

```
NEW ──[Codex 优化]──> PROMPT_READY ──[执行]──> DONE ──[Codex 验收]──> PASS ✅
                                                                   └─> FAIL ──> 分数提升：NEW (round+1) ↺
                                                                             └─> 未提升：回退最佳版本并停止
```

| 状态 | 含义 | 下一个动作 |
|---|---|---|
| `NEW` | 需求已入队 | 调用 Codex 生成 prompt |
| `PROMPT_READY` | prompt 就绪，等待执行 | 执行者接手 |
| `WAITING_EXECUTE` | 等待 WorkBuddy / TRAE 文件接力 | 等待中 |
| `DONE` | 产出已落盘 | 调用 Codex 验收 |
| `PASS` | 验收通过 | 归档 |
| `FAIL` | 验收未过，已生成返工意见 | 分数严格提升才进入下一轮，否则回退最佳 prompt 并停止 |

**护栏**：`MAX_ROUNDS = 3`。超过 3 轮仍失败则停机并告警 —— 无限重试是自动化里最贵的坑。

## 七、写 prompt 的硬性要求

Codex 产出的每个 prompt 必须包含这五段，缺一不可：

1. **目标** —— 一句话说清要什么
2. **上下文** —— 背景、约束、已有材料
3. **产出规格** —— 明确的文件路径与格式
4. **验收标准** —— 可判定的、二值的（是/否），不写"尽量好"这种无法判定的话
5. **禁止事项** —— 明确不要做什么

第 4 条最关键：**验收标准不可量化，整条流水线就退化成仪式。**

## 八、提示词优化与评分协议

1. 第 1 轮生成的 `acceptance:` 清单是本任务的固定评测标准，后续出题者不得删改或新增评分项。
2. 第 1 轮建立基线。之后每次返工只针对验收报告指出的一个主要问题改一处，避免一次改动过多而无法归因。
3. 验收者是独立角色，每项等权评分：`overall_score = 通过项数 / 固定标准总数 × 100`，四舍五入；只有所有标准通过时才给 `PASS` 和 100 分。
4. 通过的候选版本作为当前最佳；失败候选若没有严格超过历史最佳，编排器恢复最佳 prompt 并停止本任务的自动优化。任务最多 3 轮。
5. 每轮提示词和验收报告分别归档于 `_state/prompt_versions/` 与 `_state/evaluations/`。人工重置只开启新的运行批次，不删除旧快照。

该回路使用固定验收清单评估实际任务产出，不等同于固定测试集上的统计 A/B。适合可以安全重试的任务；需要严谨基准比较时，为具体任务另备可重复测试样例或评分脚本。

## 九、常见失败模式

| 症状 | 根因 | 解法 |
|---|---|---|
| 验收永远通过 | 验收者 = 执行者 | 执行者与验收者分开 |
| 无限返工 | 验收标准含糊 | 重写标准，要求二值判定 |
| 两个进程抢同一任务 | 无锁 | 编排器内置文件锁 |
| 流水线卡死 | 某环节无产出 | 每步超时 + 失败停机 |
